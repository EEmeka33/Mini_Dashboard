\subsection{Installation en 3 etapes}

Pour une nouvelle installation de Raspberry Pi OS Bookworm, executer :

\begin{enumerate}
  \item \textbf{Cloner le depôt et les sous-modules}
  \begin{lstlisting}[style=bashcode]
git clone --recursive \
    https://github.com/EEmeka33/Mini_Dashboard.git
cd Mini_Dashboard
  \end{lstlisting}
  \emph{Note:} L'option \texttt{--recursive} remplace les deux commandes separees
  \texttt{git submodule update --init --recursive}, simplifiant le processus.

  \item \textbf{Installation et configuration automatisée (SETUP.sh)}
  \begin{lstlisting}[style=bashcode]
bash SETUP.sh
  \end{lstlisting}
  Duree: ~5-10 minutes. Installe paquets, configure services systemd et le daemon RFCOMM.

  Le script installe et active automatiquement :
\begin{itemize}
    \item \texttt{bluetooth.service} pour BlueZ (avec un \texttt{main.conf} valide pour BlueZ~5)
    \item \texttt{ofono.service} pour les appels HFP
    \item \texttt{nav-bind.service} pour le daemon RFCOMM
    \item \texttt{pulseaudio} pour la musique Bluetooth
    \item l'ajout de \texttt{pi5} aux groupes \texttt{bluetooth} et \texttt{dialout}
    \item le retrait du widget Bluetooth de la barre des taches (voir section~\ref{sec:popup})
\end{itemize}

  \textbf{Important :} se deconnecter puis se reconnecter (ou redemarrer) une fois apres
  \texttt{SETUP.sh}, pour que les nouveaux groupes soient pris en compte.

  \item \textbf{Compiler le dashboard}
  \begin{lstlisting}[style=bashcode]
cd lv_port_pc_vscode
rm -rf build
mkdir build
cd build
cmake ..
make -j4
  \end{lstlisting}

  \item \textbf{Vérifier que les services système tournent}
  \begin{lstlisting}[style=bashcode]
sudo systemctl status bluetooth.service
sudo systemctl status ofono.service
sudo systemctl status nav-bind.service
  \end{lstlisting}
  Tous les trois doivent montrer \texttt{active (running)}.

  \item \textbf{Lancer le fichier compilé :}
  \begin{lstlisting}[style=bashcode]
cd lv_port_pc_vscode/bin/
./main
  \end{lstlisting}

  \item \textbf{Quitter le dashboard} : touche \textbf{Échap} (ou \textbf{Ctrl+Q}) dans
  l'application, \textbf{Ctrl+C} dans le terminal, ou \texttt{systemctl -{}-user stop dashboard}.
  Le processus se termine proprement et rend l'ecran au bureau.

\end{enumerate}

\section{Vue d'ensemble du système}
%% ===========================================================================

Le projet Mini Dashboard est un tableau de bord automobile embarqué tournant sur Raspberry Pi~5
Sous un écran circulaire $1080\times1080$ pixels. Il agrège trois flux de données en temps réel :

\begin{itemize}
  \item \textbf{Navigation} : données de Google Maps relayées depuis un smartphone Android via
    Bluetooth RFCOMM (profil SPP), lues sur \texttt{/dev/rfcomm1} sous forme de lignes JSON.
  \item \textbf{Musique Bluetooth} : métadonnées A2DP/AVRCP et jaquette, obtenues par D-Bus via
    \texttt{org.bluez.MediaPlayer1}.
  \item \textbf{Appels HFP} : détection et gestion des appels entrants via oFono et
    \texttt{org.ofono.VoiceCallManager}.
\end{itemize}

\midrule

\subsection{Arrêt propre du dashboard}
\label{sec:arret}

En v3, le pilote SDL de LVGL avait ete modifie pour ne plus appeler \texttt{exit()} sur
\texttt{SDL\_QUIT}, mais \texttt{main()} tournait en \texttt{while(1)} sans jamais le
detecter. De plus, SDL installe ses propres gestionnaires de signaux et transforme
Ctrl+C en evenement \texttt{SDL\_QUIT}. Resultat : le processus ne s'arretait jamais.

La v4 procede ainsi :
\begin{enumerate}
  \item \texttt{SDL\_SetHint(SDL\_HINT\_NO\_SIGNAL\_HANDLERS, "1")} avant l'initialisation
    de SDL, puis gestionnaires \texttt{sigaction} pour SIGINT, SIGTERM et SIGHUP qui
    positionnent le drapeau \texttt{g\_quit}.
  \item Un filtre d'evenements SDL (\texttt{SDL\_SetEventFilter}) intercepte
    \texttt{SDL\_QUIT}, la fermeture de fenetre, Échap et Ctrl+Q. Ces evenements sont
    supprimes pour que LVGL ne detruise pas l'affichage pendant qu'un timer l'utilise.
  \item La boucle principale tourne tant que \texttt{app\_running()} est vrai.
  \item À la sortie : arret de l'agent Bluetooth (desenregistrement, Pi rendu invisible),
    reveil des threads par \texttt{SIGUSR1} (interrompt un \texttt{open()} ou \texttt{poll()}
    bloquant), \texttt{pthread\_timedjoin\_np()} avec 3~s maximum par thread, puis
    \texttt{lv\_sdl\_quit()}.
  \item Filet de securite : \texttt{alarm(6)} termine le processus si une etape bloque.
\end{enumerate}

\section{Pair Button et agent d'appairage Bluetooth}
%% ===========================================================================

\subsection{Principe : un agent BlueZ integre au dashboard}

Quand un telephone demande a s'appairer, BlueZ interroge l'\emph{agent par defaut}
(\texttt{org.bluez.Agent1}) pour obtenir une confirmation. En v3, cet agent etait celui
du bureau Pi OS, qui affichait une fenetre de confirmation et faisait sortir le dashboard
du plein ecran.

En v4, le dashboard enregistre son propre agent (\texttt{src/bt\_agent.c}) et le declare
agent par defaut via \texttt{AgentManager1.RequestDefaultAgent}. BlueZ lui envoie donc
toutes les demandes, auxquelles il repond sans aucune fenetre. L'agent reaffirme sa place
toutes les 15~s, au cas ou le bureau la reprendrait, et se desenregistre a la fermeture.

\begin{lstlisting}[style=ccode,caption={bt\_agent.h --- API publique (non bloquante)}]
#define BT_PAIR_WINDOW_S 180

int  bt_agent_start(void);               /* lance le thread agent      */
void bt_agent_stop(void);                /* desenregistre et arrete    */
void bt_agent_open_pairing_window(void); /* appele par le bouton Pair  */
void bt_agent_get_status(char *buf, size_t len); /* texte sous Pair    */
\end{lstlisting}

Tout le travail D-Bus est fait dans un thread dedie ; l'UI ne fait que poser une demande.
Ce module remplace \texttt{bt\_pairing.h} et l'appel a \texttt{bt\_make\_discoverable.sh}.

\subsection{Fenetre d'appairage (bouton Pair)}

Un appui sur \textbf{Pair} :
\begin{enumerate}
  \item met l'adaptateur sous tension (\texttt{Powered}) ;
  \item regle \texttt{DiscoverableTimeout} et \texttt{PairableTimeout} a 180~s ;
  \item active \texttt{Pairable} et \texttt{Discoverable} sur \texttt{org.bluez.Adapter1} ;
  \item affiche le compte a rebours sous le bouton (\og Visible 2:59 - pair from your phone\fg{}).
\end{enumerate}

Pendant la fenetre, l'agent verifie chaque seconde les appareils BlueZ. Des qu'un
telephone devient \texttt{Paired}, il est marque \texttt{Trusted} (reconnexions futures
sans autorisation), une connexion est lancee (\texttt{Device1.Connect}), la fenetre se
ferme et le dashboard affiche \og Paired: <nom>\fg{}.

\subsection{Regles d'acceptation}

\begin{center}
\begin{tabular}{lll}
\toprule
\textbf{Requete BlueZ} & \textbf{Fenetre ouverte} & \textbf{Fenetre fermee} \\
\midrule
\texttt{RequestConfirmation} & acceptee & refusee \\
\texttt{RequestAuthorization} & acceptee & refusee \\
\texttt{RequestPinCode} & \texttt{"0000"} & refusee \\
\texttt{RequestPasskey} & \texttt{0} & refusee \\
\texttt{AuthorizeService} & acceptee & acceptee si deja appaire \\
\bottomrule
\end{tabular}
\end{center}

\textbf{Securite :} hors de la fenetre de 3~minutes, aucun nouvel appareil ne peut
s'appairer. Seuls les telephones deja appaires peuvent se reconnecter.

\subsection{Parametres (\texttt{bt\_agent.c})}

\begin{lstlisting}[style=ccode,caption={bt\_agent.c --- configuration}]
#define AGENT_PATH        "/org/minidashboard/agent"
#define AGENT_CAPABILITY  "NoInputNoOutput"
#define BT_ALIAS          NULL     /* ex: "Mini Dashboard" */
#define DBUS_TIMEOUT_MS   3000
\end{lstlisting}

\begin{description}
  \item[\texttt{NoInputNoOutput}] Appairage \emph{Just Works} : le telephone demande
    seulement \og Associer ?\fg{}.
  \item[\texttt{DisplayYesNo}] Comparaison de code : le code s'affiche sur le telephone,
    le Pi le confirme automatiquement.
  \item[\texttt{BT\_ALIAS}] Nom visible depuis le telephone ; \texttt{NULL} conserve le nom
    du Pi (\og raspberrypi\fg{}).
\end{description}

\subsection{Popup \og Pairing successful\fg{} du bureau Pi OS}
\label{sec:popup}

Meme avec l'agent integre, le \textbf{widget Bluetooth de la barre des taches} affichait
encore une fenetre \og Pairing successful / Connection successful\fg{}. Ce widget
(\texttt{lxplug-bluetooth}) surveille tous les appareils BlueZ et ouvre sa propre fenetre
GTK des qu'un appareil passe a \texttt{Paired}, quel que soit l'agent qui a accepte.
Le dashboard ne peut donc pas l'empecher : il faut retirer le widget.

Le script \texttt{disable\_panel\_bluetooth.sh}, appele par \texttt{SETUP.sh}, le retire
pour les deux bureaux de Pi OS :
\begin{itemize}
  \item \textbf{Wayland} (\texttt{wf-panel-pi}) : supprime \texttt{bluetooth} de la cle
    \texttt{widgets\_right} dans le fichier\\
    \path{~/.config/wf-panel-pi/wf-panel-pi.ini} ;
  \item \textbf{X11} (\texttt{lxpanel-pi}) : supprime le bloc \texttt{Plugin \{ type=bluetooth \}}
    du fichier\\
    \path{~/.config/lxpanel-pi/panels/panel}.
\end{itemize}

\begin{lstlisting}[style=bashcode]
bash disable_panel_bluetooth.sh            # retire le widget (sans sudo, en pi5)
bash disable_panel_bluetooth.sh --restore  # remet la configuration d'origine
\end{lstlisting}

Le Bluetooth continue de fonctionner (\texttt{bluetoothd} est un service systeme) ;
seule l'icone de la barre des taches disparait.

\subsection{Appairage initial du telephone}

\subsubsection{Methode 1 : Via le bouton Pair du dashboard (RECOMMANDÉE)}

\begin{enumerate}
  \item \textbf{Lancer le dashboard} : \texttt{./main} depuis \texttt{lv\_port\_pc\_vscode/bin}
  \item \textbf{Cliquer sur le bouton bleu \og Pair\fg{}} : le Pi devient visible 3~minutes
  \item \textbf{Sur le telephone} : Parametres $\to$ Bluetooth $\to$ Associer un appareil
  \item \textbf{Selectionner \og raspberrypi\fg{}} et accepter \textbf{sur le telephone uniquement}
  \item Le dashboard affiche \og Paired: <nom du telephone>\fg{} ; aucune fenetre ne s'ouvre sur le Pi
\end{enumerate}

\emph{Avantage :} aucune ligne de commande, aucune confirmation sur le Pi, le plein ecran
est conserve. Le telephone est automatiquement \texttt{Trusted} et son adresse MAC est
detectee par \texttt{main.c}.

\subsubsection{Methode 2 : En ligne de commande (manuel)}

\begin{lstlisting}[style=bashcode]
sudo bluetoothctl
[bluetooth]# power on
[bluetooth]# agent on
[bluetooth]# default-agent
[bluetooth]# scan on
\end{lstlisting}

Attendre que le telephone apparaisse :

\begin{verbatim}
[NEW] Device 2C:BE:EB:7F:2D:FA Pixel 7
\end{verbatim}

Continuer l'appairage :

\begin{lstlisting}[style=bashcode]
[bluetooth]# scan off
[bluetooth]# pair 2C:BE:EB:7F:2D:FA
\end{lstlisting}

Confirmer le PIN sur le telephone (ou pas si le Pi envoie le PIN automatiquement).

\begin{lstlisting}[style=bashcode]
[bluetooth]# trust 2C:BE:EB:7F:2D:FA
[bluetooth]# connect 2C:BE:EB:7F:2D:FA
[bluetooth]# quit
\end{lstlisting}

\emph{Note :} \texttt{bluetoothctl default-agent} prend la place de l'agent du dashboard
jusqu'a la prochaine reaffirmation (15~s maximum). Apres appairage, l'adresse MAC est
sauvegardee par \texttt{main.c} dans \texttt{/tmp/connected\_phone\_mac.txt}.

\subsection{Configuration BlueZ pour la musique et les appels}

\subsubsection{Fichier \texttt{main.conf} ecrit par \texttt{SETUP.sh}}

La version precedente de \texttt{SETUP.sh} ecrivait des cles que BlueZ~5 ne connait pas
(\texttt{Enable=Source}, \texttt{HandsfreeDevice}, \texttt{Trustable}) et qui etaient
ignorees. La v4 ecrit uniquement des cles valides (l'ancien fichier est sauvegarde une
seule fois dans \texttt{main.conf.orig}) :

\begin{lstlisting}[style=confcode,caption={/etc/bluetooth/main.conf (v4)}]
[General]
# Classe "Car audio" : le telephone voit le Pi comme un autoradio
Class = 0x200420
# Fenetre d'appairage ouverte par le bouton Pair (secondes)
DiscoverableTimeout = 180
PairableTimeout = 0
# Re-appairage sans confirmation si le telephone a "oublie" le Pi
JustWorksRepairing = always
FastConnectable = true

[Policy]
# Adaptateur allume au demarrage + reconnexion auto au telephone connu
AutoEnable = true
ReconnectAttempts = 7
ReconnectIntervals = 1,2,4,8,16,32,64
\end{lstlisting}

\textbf{Note sur \texttt{Disable=Headset} :} cette directive vient de BlueZ~4
(\texttt{audio.conf}) et n'est pas reconnue par BlueZ~5. Sous Bookworm, c'est la
configuration PipeWire de la section~\ref{sec:pipewire} qui confie le HFP a oFono.

\subsection{Configuration PipeWire pour HFP via oFono}
\label{sec:pipewire}

Sur Raspberry Pi OS Bookworm, PipeWire remplace PulseAudio. Pour que les appels HFP
passent par oFono :

\section{Daemon de liaison RFCOMM : \texttt{nav-bind-daemon.sh}}
%% ===========================================================================

\subsection{Rôle et perimetre}

\texttt{nav-bind-daemon.sh} est le seul demon specifique au projet côte Raspberry Pi.
Il maintient en permanence le binding entre \texttt{/dev/rfcomm1} et le service
\texttt{NavJsonService} de l'application Android NavRelay.

Le numero de canal RFCOMM assigne dynamiquement par Android peut varier à chaque
reconnexion ; il ne peut être connu qu'en consultant le registre SDP du telephone
à la volee, d'où la necessite de ce demon.

\subsection{Variables de configuration}

A partir de la version amelioree du daemon, le MAC du telephone est detecte automatiquement
par \texttt{main.c} et ecrit dans le fichier \texttt{/tmp/connected\_phone\_mac.txt}.

\begin{lstlisting}[style=bashcode,caption={nav-bind-daemon.sh --- detection auto du MAC}]
MAC_FILE="/tmp/connected_phone_mac.txt"
if [ -f "$MAC_FILE" ]; then
  PHONE_MAC=$(cat "$MAC_FILE" 2>/dev/null)
else
  PHONE_MAC="2C:BE:EB:7F:2D:FA"  # Fallback si fichier absent
fi
TARGET_SERVICE_NAME="NavJsonService"
\end{lstlisting}

\emph{Avantage:} Plus besoin de modifier manuellement le MAC. Le daemon se reconfigure
automatiquement lors du reconnexion d'un telephone different.

\textbf{Comment ca marche:}
\begin{enumerate}
  \item \texttt{main.c} detecte le telephone connecte via D-Bus (org.bluez.Device1).
  \item \texttt{main.c} extrait l'adresse MAC et l'ecrit dans \texttt{/tmp/connected\_phone\_mac.txt}
    (verification toutes les 5~s ; ecriture uniquement si l'adresse change, via un fichier
    temporaire puis \texttt{rename()} pour que le daemon ne lise jamais un fichier incomplet).
  \item Le daemon relance la lecture du fichier chaque cycle (5 secondes).
  \item Si le MAC change (nouveau telephone), le daemon se reconfigure automatiquement.
\end{enumerate}

\subsection{Logique de binding detaillee}

Le script tourne dans une boucle infinie avec 5 secondes d'attente entre chaque cycle.

\subsubsection{etape 1 : lecture de l'etat courant de rfcomm1}

\begin{lstlisting}[style=bashcode, showstringspaces=false]
CURRENT_LINE=$(rfcomm | awk -v mac="$PHONE_MAC" \
  '$1=="rfcomm1:" && $2==mac {print $0}')
\end{lstlisting}

La sortie de \texttt{rfcomm} ressemble à :
\begin{verbatim}
rfcomm1: 2C:BE:EB:7F:2D:FA channel 7 config
\end{verbatim}

Si aucune ligne ne correspond, \texttt{CURRENT\_LINE} est vide et un rebind
sera declenche.

\subsubsection{etape 2 : consultation SDP du telephone}

\begin{lstlisting}[style=bashcode, showstringspaces=false]
SDP_OUTPUT=$(sdptool browse "$PHONE_MAC" 2>/dev/null || true)

TARGET_CHANNEL=$(printf '%s\n' "$SDP_OUTPUT" \
  | awk -v name="$TARGET_SERVICE_NAME" '
    $0 ~ "Service Name: "name { in_block=1 }
    in_block && /Channel:/ { print $2; exit }
  ')
\end{lstlisting}

\texttt{sdptool browse} parcourt tous les services Bluetooth du telephone. Si
\texttt{TARGET\_CHANNEL} est vide (NavRelay non demarre ou telephone hors portee),
le cycle recommence apres 5~s.

\subsubsection{etape 3 : decision de rebinding}

Trois cas declenchent un rebind :

\begin{itemize}
  \item \texttt{rfcomm1} n'existe pas ou n'est pas associe à \texttt{PHONE\_MAC}.
  \item \texttt{rfcomm1} existe mais est en etat \texttt{closed}.
  \item \texttt{rfcomm1} existe mais pointe sur un canal different de
    \texttt{TARGET\_CHANNEL}.
\end{itemize}

\subsubsection{etape 4 : rebinding}

\begin{lstlisting}[style=bashcode]
rfcomm release 1 2>/dev/null || true
rfcomm bind 1 "$PHONE_MAC" "$TARGET_CHANNEL"
\end{lstlisting}

Apres un bind reussi, \texttt{/dev/rfcomm1} est disponible et
\texttt{nav\_thread\_fn()} peut l'ouvrir.

\subsection{Installation comme service systemd}

\begin{lstlisting}[style=bashcode]

\end{lstlisting}

\begin{lstlisting}[style=confcode,caption={/etc/systemd/system/nav-bind.service}]

\subsection{Diagnostic et depannage}

\begin{description}
  \item[\texttt{sdptool returned nothing}]
    Le telephone n'est pas connecte. Verifier :
    \texttt{bluetoothctl info 2C:BE:EB:7F:2D:FA} (champ \texttt{Connected: yes}).
  \item[\texttt{cannot find service "NavJsonService"}]
    NavRelay n'est pas demarre. Ouvrir NavRelay et appuyer sur \og Start \fg{}.
  \item[\texttt{rfcomm bind failed}]
    Module noyau manquant : \texttt{sudo modprobe rfcomm}.
    Verifier aussi que le service tourne en root.
  \item[\texttt{/dev/rfcomm1} introuvable apres binding]
    Ajouter l'utilisateur au groupe \texttt{dialout} :
    \texttt{sudo usermod -aG dialout pi5}, puis se reconnecter.
  \item[rfcomm1 se rebind en boucle]
    Qualite de signal Bluetooth insuffisante ou telephone non marque comme
    de confiance (\texttt{trust} dans \texttt{bluetoothctl}).
\end{description}

\subsection{\texttt{NavServer} : serveur Bluetooth RFCOMM}

\subsubsection{UUID et nom de service}

\begin{lstlisting}[style=ktcode,caption={NavServer.kt --- constantes}]
private const val SERVICE_NAME = "NavJsonService"
val SPP_UUID: UUID =
    UUID.fromString("00001101-0000-1000-8000-00805F9B34FB")
\end{lstlisting}

L'UUID \texttt{00001101-...} est l'UUID standardise du \emph{Serial Port Profile} (SPP).
\texttt{NavJsonService} est le nom que \texttt{nav-bind-daemon.sh} recherche dans le
registre SDP. Ces deux valeurs doivent rester coherentes.

\subsubsection{Cycle de vie du serveur}

\texttt{start()} lance un thread qui :

\begin{enumerate}
  \item Recupere l'adaptateur Bluetooth ; s'il est eteint, l'etat affiche
    \og Bluetooth is OFF\fg{} et le thread reessaie toutes les 2~s.
  \item Appelle \texttt{listenUsingRfcommWithServiceRecord(SERVICE\_NAME, SPP\_UUID)},
    enregistrant le service dans le registre SDP avec un canal assigne dynamiquement.
    C'est ce canal que le daemon decouvre via \texttt{sdptool}.
  \item Boucle sur \texttt{accept()} pour accepter la connexion du Raspberry Pi.
    À chaque reconnexion, l'ancienne socket et son flux sont fermes et remplaces.
  \item En cas d'erreur du serveur, il est recree automatiquement apres 2~s.
\end{enumerate}

\subsubsection{Envoi des messages JSON}

\begin{lstlisting}[style=ktcode,caption={NavServer.kt --- send()}]
fun send(json: JSONObject) {
    val out = outRef.get() ?: return      // Pi pas encore connecte
    try {
        val line = json.toString() + "\n"
        out.write(line.toByteArray(Charsets.UTF_8))
        out.flush()
        sentCount++
    } catch (e: Exception) {
        // Le Pi s'est deconnecte : on ferme SEULEMENT ce client,
        // le serveur continue d'accepter les connexions.
        dropClient()
        if (running) state = "Waiting for the Pi..."
    }
}
\end{lstlisting}

Chaque message est une ligne JSON terminee par \verb|\n| en UTF-8.

\textbf{Correction v4 :} en v3, une erreur d'ecriture appelait \texttt{stop()}, ce qui
arretait definitivement le serveur. Chaque redemarrage du dashboard (qui ferme
\texttt{/dev/rfcomm1}) coupait donc la navigation jusqu'a un nouvel appui sur Start.

\subsection{\texttt{MapsNotificationListener}}

\subsubsection{Interception des notifications}

\texttt{onNotificationPosted()} filtre les notifications dont le \texttt{packageName}
est \texttt{"com.google.android.apps.maps"}. Une notification de navigation typique (FR) :

\begin{center}
\begin{tabular}{lll}
\toprule
\textbf{Champ} & \textbf{Exemple} & \textbf{Role} \\
\midrule
\texttt{EXTRA\_TITLE} & \og 300~m\fg{} & distance avant la manoeuvre \\
\texttt{EXTRA\_TEXT} & \og Tournez à droite sur Rue X\fg{} & prochaine action \\
\texttt{EXTRA\_SUB\_TEXT} & \og 12~min · 4,5~km · Arrivée à 14:32\fg{} & ETA \\
\bottomrule
\end{tabular}
\end{center}

La disposition varie selon la version de Maps (la distance peut etre dans la meme ligne
que l'action : \og 300~m · Tournez à droite\fg{}). Le listener ne se fie donc pas a la
position des champs mais \textbf{classe le contenu}.

\subsubsection{Lecture des textes : \texttt{getCharSequence()}}

Maps place du texte formate (\texttt{SpannableString}) dans le titre. En v3, le titre etait
lu avec \texttt{getString()}, qui renvoie \texttt{null} dans ce cas : la distance etait
perdue (d'ou \og 0~m\fg{}) et la ligne d'ETA etait prise comme action. La v4 lit tous les
champs avec \texttt{getCharSequence()} :

\begin{lstlisting}[style=ktcode]
private fun Bundle.text(key: String): String =
    getCharSequence(key)?.toString()?.trim().orEmpty()
\end{lstlisting}

Champs lus, par ordre de priorite : \texttt{EXTRA\_TITLE}, \texttt{EXTRA\_TITLE\_BIG},
\texttt{EXTRA\_TEXT}, \texttt{EXTRA\_BIG\_TEXT}, \texttt{EXTRA\_TEXT\_LINES},
\texttt{EXTRA\_SUB\_TEXT}, \texttt{EXTRA\_INFO\_TEXT}.

\subsubsection{Classement : ETA, distance, action}

\begin{enumerate}
  \item \textbf{ETA} : une ligne est classee ETA si elle contient une heure
    (\texttt{14:32}, \texttt{14 h 32}), une duree (\texttt{12 min}, \texttt{1 h}) ou le mot
    \og arrivée\fg{} / \og ETA\fg{}. Elle n'est jamais utilisee comme action ni comme
    distance (sinon la distance totale \og 4,5~km\fg{} remplacerait celle de la manoeuvre).
  \item \textbf{Distance} : premiere distance trouvee dans les lignes non-ETA.
  \item \textbf{Action} : premiere ligne non-ETA qui contient autre chose qu'une distance ;
    une distance en tete (\og 300~m · \fg{}) est retiree.
  \item \textbf{Filet de securite} : si rien n'est reconnu, la premiere ligne est envoyee
    telle quelle (comportement v3) plutot que de ne rien envoyer.
\end{enumerate}

\begin{lstlisting}[style=ktcode,caption={MapsNotificationListener.kt --- expressions regulieres}]

\subsubsection{Extraction de la distance}

\texttt{parseDistanceMeters()} reconnait \og \texttt{320 m}\fg{}, \og \texttt{1,2 km}\fg{},
\og \texttt{1.2 km}\fg{}, ainsi que \texttt{mi}, \texttt{ft} et \texttt{yd}. Tout est converti
en metres ; la fonction renvoie \texttt{-1} si aucune distance n'est trouvee.

ecrasaient la meme variable globale \texttt{dbus\_conn}.

\subsection{Thread de navigation : \texttt{nav\_thread\_fn()}}

\subsubsection{Connexion et reconnexion à \texttt{/dev/rfcomm1}}

\begin{lstlisting}[style=ccode,caption={main.c --- boucle de lecture rfcomm1 (v4)}]
while (app_running()) {
    if (fd < 0) {
        /* bloque jusqu'a la connexion ; SIGUSR1 l'interrompt a l'arret */
        fd = open("/dev/rfcomm1", O_RDONLY | O_NOCTTY);
        if (fd < 0) { sleep_ms_interruptible(2000, NULL); continue; }
        fcntl(fd, F_SETFL, fcntl(fd, F_GETFL) | O_NONBLOCK);
    }
    struct pollfd pfd = { .fd = fd, .events = POLLIN };
    int pr = poll(&pfd, 1, 500);   /* reveil periodique pour l'arret */
    if (pr == 0 || (pr < 0 && errno == EINTR)) continue;
    ssize_t n = read(fd, buf + used, sizeof(buf) - 1 - used);
    if (n <= 0) { /* EOF / HUP : fermeture et reconnexion */ }
    /* decoupage par '\n' puis nav_handle_line() pour chaque ligne */
}
\end{lstlisting}

Le port est ouvert avec \texttt{O\_NOCTTY} pour eviter d'en faire le terminal de
contrôle du processus. Le \texttt{poll()} de 500~ms (au lieu de \texttt{fgets()} bloquant)
permet au thread de s'arreter rapidement a la fermeture du dashboard.

\texttt{nav\_handle\_line()} parse la ligne hors verrou dans une copie locale, puis la
recopie dans \texttt{g\_state.nav}. Le terminal affiche une ligne a chaque changement :

\begin{verbatim}
Nav updated: 300 m | Tournez a droite sur Rue X | 12 min - 4,5 km - ...
\end{verbatim}

\subsubsection{Parsing JSON}

\texttt{parse\_nav\_json()} utilise \texttt{json\_tokener\_parse()} de \texttt{json-c}.
Elle extrait \texttt{next\_action}, \texttt{distance\_to\_next\_m}, \texttt{eta},
\texttt{street\_name}, \texttt{speed\_kmh}, \texttt{lat}, \texttt{lon} et remplit
\texttt{nav\_info\_t}. La ligne du bas affiche \texttt{street\_name} s'il est fourni,
sinon l'ETA.

\subsection{Thread musique : \texttt{music\_thread\_fn()}}

\subsubsection{Connexion D-Bus et decouverte du lecteur}

\texttt{dbus\_open\_private("music")} ouvre une connexion privee au bus systeme (nouvel
essai toutes les 2~s si le bus est indisponible).

\texttt{find\_player\_path()} envoie \texttt{GetManagedObjects} à \texttt{org.bluez}
sur \texttt{/} et cherche le premier objet exposant \texttt{org.bluez.MediaPlayer1}.
Le chemin resultant est de la forme :

\begin{verbatim}
/org/bluez/hci0/dev_2C_BE_EB_7F_2D_FA/player0
\end{verbatim}

\textbf{Redecouverte automatique (v4) :} tant qu'aucun lecteur n'est connu, la recherche
est relancee toutes les 3~s (\texttt{REDISCOVER\_PERIOD\_S}). Si \texttt{GetAll} echoue
(telephone deconnecte, \texttt{player0} devenu \texttt{player1}...), le chemin est oublie
et la recherche reprend ; l'UI affiche \og No MediaPlayer / Searching...\fg{}. Il n'est
donc plus necessaire de relancer le dashboard apres le premier appairage.

\subsubsection{Lecture des proprietes}

Toutes les secondes, \texttt{get\_music\_properties()} appelle
\texttt{GetAll("org.bluez.MediaPlayer1")} et extrait :

\begin{itemize}
  \item \texttt{Status} (chaîne) $\to$ \texttt{g\_state.music.status}
  \item \texttt{Position} (uint32, ms) $\to$ \texttt{g\_state.music.position\_ms}
  \item \texttt{Track} (dict) $\to$ \texttt{Title}, \texttt{Artist}, \texttt{Album},
    \texttt{Duration}
\end{itemize}

En cas de changement de piste (couple titre+artiste), une demande est transmise au
\textbf{thread jaquette} (\texttt{cover\_thread\_fn()}, file d'une requete protegee par
\texttt{g\_cover\_lock} et \texttt{g\_cover\_cond}). Le telechargement, qui peut prendre
plusieurs secondes, ne bloque ainsi ni les boutons musique ni l'UI. Une fois la jaquette
ecrite, \texttt{g\_state.cover\_version} est incremente.

\subsubsection{Commandes de contrôle}

Les boutons LVGL ne font plus d'appel D-Bus : ils posent une commande dans
\texttt{g\_state.media\_cmd}. Le thread musique la lit a chaque tour (toutes les 200~ms)
et appelle \texttt{send\_player\_method()}, qui envoie \texttt{Play}, \texttt{Pause},
\texttt{Next} ou \texttt{Previous} à \texttt{org.bluez.MediaPlayer1} (timeout 3~s).

\subsection{Thread appels : \texttt{calls\_thread\_fn()}}

\subsubsection{Decouverte du modem HFP}

\texttt{find\_modem\_with\_voicecall()} interroge
\texttt{org.ofono.Manager.GetModems()} et selectionne le modem dont la liste
d'interfaces contient \texttt{"org.ofono.VoiceCallManager"} :

\begin{verbatim}
/hfp/org/bluez/hci0/dev_2C_BE_EB_7F_2D_FA
\end{verbatim}

Comme pour la musique, la recherche est relancee toutes les 3~s tant qu'aucun modem
n'est trouve, et apres tout echec de \texttt{GetCalls}. Si un modem HFP est present mais
eteint (\texttt{Powered = false}), il est allume via \texttt{Modem.SetProperty("Powered", true)} ;
\texttt{VoiceCallManager} apparait alors au tour suivant.

\subsubsection{Polling des appels}

Toutes les secondes, \texttt{get\_calls()} envoie
\texttt{VoiceCallManager.GetCalls()} et extrait pour chaque appel \texttt{State},
\texttt{LineIdentification} et \texttt{Name}. Le thread met à jour
\texttt{has\_incoming\_call} si un appel est en etat \texttt{"incoming"} ou
\texttt{"waiting"}.

\subsubsection{Decrocher et raccrocher}

Les boutons posent \texttt{CALL\_ANSWER} ou \texttt{CALL\_HANGUP} dans
\texttt{g\_state.call\_cmd} (avec le chemin de l'appel) et masquent le panneau
immediatement. Le thread appels execute ensuite \texttt{call\_voicecall\_method()},
qui envoie \texttt{Answer} ou
\texttt{Hangup} à \texttt{org.ofono.VoiceCall} (timeout 3~s).

\subsection{Timer UI (100~ms)}

\begin{lstlisting}[style=ccode,caption={main.c --- callback du timer LVGL (v4)}]
static void ui_update_timer(lv_timer_t *timer) {
    /* Copie rapide sous verrou, puis travail LVGL sans verrou */
    pthread_mutex_lock(&g_state.lock);
    nav = g_state.nav;   music = g_state.music;   call = g_state.current_call;
    cover_version = g_state.cover_version;  /* ... */
    pthread_mutex_unlock(&g_state.lock);

    update_nav_display(&nav, nav_connected);
    update_music_display(&music, cover_version);
    update_call_display(incoming, &call);
    speedo_set_speed((int32_t)nav.speed);
    bt_agent_get_status(status, sizeof(status));   /* texte sous Pair */
}
\end{lstlisting}

\begin{description}
  \item[\texttt{update\_nav\_display()}]
    Instruction, distance (\og -{}- m\fg{} si inconnue, sinon m arrondis a 10~m au-dela de
    100~m, ou km), puis nom de rue ou ETA sur la ligne du bas.
  \item[\texttt{update\_music\_display()}]
    Titre, artiste, label Play/Pause. La jaquette n'est rechargee que si
    \texttt{cover\_version} a change (en v3 : decodage JPEG toutes les 100~ms), apres
    \texttt{lv\_image\_cache\_drop()} pour ne pas reafficher l'ancienne image en cache.
  \item[\texttt{update\_call\_display()}]
    Affiche/masque le panneau (\texttt{LV\_OBJ\_FLAG\_HIDDEN}), nom ou
    \og Unknown\fg{} et numero de telephone.
  \item[\texttt{speedo\_set\_speed()}]
    Compteur mis à jour avec la vitesse en km/h entier.
\end{description}

Tous les textes passent par \texttt{label\_set\_if\_changed()}, qui n'appelle
\texttt{lv\_label\_set\_text()} que si le texte a change (evite des redessins inutiles).

\subsubsection{Accents et polices LVGL}

Les polices Montserrat integrees a LVGL ne couvrent que l'ASCII : \og Tournez à droite\fg{}
s'afficherait \og Tournez  droite\fg{}. \texttt{fold\_to\_ascii()} decode l'UTF-8 et remplace
les caracteres accentues par leur equivalent sans accent (\og é\fg{} $\to$ \og e\fg{},
\og ç\fg{} $\to$ \og c\fg{}, \og œ\fg{} $\to$ \og oe\fg{}), les espaces insecables par des
espaces, \og ·\fg{} par \og -\fg{}, et ignore les emoji. Elle est appliquee aux textes de
navigation et de musique via \texttt{label\_set\_text\_ascii()}.

Pour afficher les vrais accents, il faudrait generer une police Montserrat incluant la
plage Latin-1 avec le convertisseur de polices LVGL (\url{https://lvgl.io/tools/fontconverter}).

void speedo_interactive_create(void);

\end{lstlisting}

\subsection{Parametres du cadran}

\begin{lstlisting}[style=ccode,caption={speedo\_interactive.c --- constantes}]
#define SPEEDO_W    1080    /* Largeur totale (px)               */
#define SPEEDO_H    1080    /* Hauteur totale (px)               */
#define SPEED_MIN   0       /* Vitesse minimale (km/h)           */
#define SPEED_MAX   260     /* Vitesse maximale (km/h)           */
#define ARC_SWEEP   180     /* Balayage angulaire total (degres) */
#define ARC_START   270     /* Angle de depart (bas du cercle)   */
\end{lstlisting}

\subsection{Conversion vitesse/angle et aiguille}

\texttt{speed\_to\_angle()} calcule l'angle par interpolation lineaire :

\[
  \theta = \texttt{ARC\_START} + \frac{v - v_{\min}}{v_{\max} - v_{\min}}
    \times \texttt{ARC\_SWEEP}
\]

\texttt{update\_needle()} convertit $\theta$ en radians, calcule les deux extremites
de l'aiguille sur la couronne externe du cadran et met à jour l'objet ligne LVGL
\texttt{needle\_line}.

\texttt{create\_ticks\_and\_labels()} cree pour chaque pas de 5~km/h :
\begin{itemize}
  \item Graduation majeure tous les 10~km/h (plus longue, couleur claire).
  \item Graduation mineure tous les 5~km/h.
  \item Label numerique (police \texttt{lv\_font\_montserrat\_18}) tous les 25~km/h.
\end{itemize}

\texttt{speedo\_interactive\_create()} cree les graduations, l'aiguille, et deux
labels centraux : la valeur numerique (police 48~pt) et l'unite \og km/h \fg{}.

\section{Recuperation de jaquette : \texttt{album\_art.c}}
%% ===========================================================================

\subsection{Signature}

\begin{lstlisting}[style=ccode]
int download_itunes_cover(const char *artist,
                          const char *album,
                          const char *out_path);
\end{lstlisting}

Dependances : \texttt{libcurl} et \texttt{json-c}. Retourne 1 en succes, 0 sinon.

\subsection{Flux d'execution}

\begin{enumerate}
  \item Encodage URL du terme (\textit{artiste} + espace + \textit{album}) via
    \texttt{curl\_easy\_escape()}.
  \item Requête GET vers :
    \url{https://itunes.apple.com/search?term=<query>&entity=album&limit=1}
  \item Accumulation de la reponse JSON en memoire via \texttt{write\_to\_memory()}
    (structure \texttt{Memory} avec \texttt{realloc()} dynamique).
  \item Extraction de \texttt{"artworkUrl100"} dans \texttt{results[0]}.
  \item Telechargement de l'image vers \texttt{out\_path} via
    \texttt{write\_to\_file()}.
\end{enumerate}

Si le telechargement echoue (pas de reseau, artiste inconnu), la fonction retourne 0
et l'ancienne jaquette reste affichee jusqu'au prochain changement de piste.

\textbf{Modifications v4 :}
\begin{itemize}
  \item \texttt{curl\_global\_init()} est appele une seule fois dans \texttt{main()} (cette
    fonction n'est pas thread-safe) et n'est plus appele a chaque telechargement.
  \item \texttt{CURLOPT\_NOSIGNAL} (obligatoire en multi-thread), \texttt{CURLOPT\_CONNECTTIMEOUT}
    de 5~s et \texttt{CURLOPT\_TIMEOUT} de 10~s (JSON) / 15~s (image) : sans reseau, le
    thread jaquette ne reste plus bloque et n'empeche pas l'arret.
  \item L'image est ecrite dans \texttt{cover.jpg.part} puis renommee (\texttt{rename()}) :
    l'UI ne lit jamais une image a moitie telechargee.
  \item La recherche utilise l'album s'il est connu, sinon le titre.
\end{itemize}

\section{Depannage general}
%% ===========================================================================

\subsection{\og Waiting for route...\fg{} en permanence}

\begin{itemize}
  \item Verifier que \texttt{/dev/rfcomm1} existe : \texttt{ls /dev/rfcomm*}
  \item Tester la reception : \texttt{cat /dev/rfcomm1} (doit afficher des lignes JSON).
  \item Verifier les permissions : \texttt{sudo usermod -aG dialout pi5}.
  \item Dans NavRelay : cliquer sur \textbf{Start}, puis lire l'ecran d'etat :
  \begin{itemize}
    \item ligne 2 \og NOT bound\fg{} : desactiver puis reactiver NavRelay dans
      \emph{Acces aux notifications} (frequent apres une reinstallation) ;
    \item ligne 3 bloquee sur \og Waiting for the Pi...\fg{} : verifier
      \texttt{journalctl -fu nav-bind} (doit afficher \texttt{bound /dev/rfcomm1 ...}) ;
    \item ligne 4 qui augmente mais rien sur le dashboard : tester \texttt{cat /dev/rfcomm1}
      dashboard ferme.
  \end{itemize}
  \item Le terminal du dashboard doit afficher \texttt{Connected to /dev/rfcomm1} puis des
    lignes \texttt{Nav updated: ...}.
\end{itemize}

\subsection{Distance \og -{}- m\fg{} ou action incorrecte}

\begin{itemize}
  \item Afficher ce que Maps envoie : \texttt{adb logcat -s NavRelay} pendant une navigation.
  \item Les lignes \texttt{title=... text=... sub=...} montrent la disposition de la
    notification ; la ligne \texttt{-> next=... dist=... eta=...} montre le classement.
  \item Si la disposition de Maps a change, adapter \texttt{DIST\_RE} / \texttt{ETA\_RE}
    dans \texttt{MapsNotificationListener.kt}.
\end{itemize}

\subsection{\og No MediaPlayer\fg{}}

\begin{itemize}
  \item Verifier A2DP avec \texttt{busctl tree org.bluez} (chercher \texttt{/player0}).
  \item Jouer un morceau sur le telephone pour que BlueZ cree \texttt{MediaPlayer1}.
  \item Le dashboard le detecte seul en moins de 3~s (message \texttt{[Music] MediaPlayer found}) ;
    il n'est plus necessaire de le redemarrer.
\end{itemize}

\subsection{Aucun appel detecte}

\begin{itemize}
  \item Verifier oFono : \texttt{systemctl status ofono}.
  \item Verifier les messages \texttt{[Calls]} dans le terminal du dashboard
    (\texttt{HFP modem found}, \texttt{Powered on modem}).
  \item Verifier l'existence de \texttt{/etc/pipewire/pipewire-pulse.conf.d/10-ofono.conf}.
  \item Tester : \texttt{busctl call org.ofono / org.ofono.Manager GetModems}.
\end{itemize}

\subsection{La jaquette ne s'affiche pas}

\begin{itemize}
  \item Tester la connectivite :
    \texttt{curl "https://itunes.apple.com/search?term=test\&entity=album\&limit=1"}
  \item Verifier que \texttt{/home/pi5/dashboard/} est accessible en ecriture.
  \item S'assurer que \texttt{libcurl} et \texttt{libjson-c} sont lies à la compilation.
\end{itemize}

\subsection{Pair Button ne fonctionne pas}

\begin{itemize}
  \item Lire les messages \texttt{[BT agent]} du dashboard : \texttt{Registered (NoInputNoOutput)}
    doit apparaitre au demarrage.
  \item \texttt{RegisterAgent failed} ou \texttt{Set ... failed} : verifier que \texttt{pi5}
    est dans le groupe \texttt{bluetooth} (\texttt{groups pi5}), puis se reconnecter.
  \item \texttt{... -> rejected (press Pair first)} : la demande est arrivee hors de la
    fenetre de 3~minutes ; rappuyer sur Pair.
  \item \og Bluetooth error\fg{} sous le bouton : l'adaptateur n'a pas pu etre rendu visible
    (\texttt{rfkill list}, \texttt{bluetoothctl show}).
\end{itemize}

\subsection{Une fenetre Bluetooth du bureau apparait encore}

\begin{itemize}
  \item Fenetre \og Pairing successful / Connection successful\fg{} : c'est le widget de la
    barre des taches ; lancer \texttt{bash disable\_panel\_bluetooth.sh} (sans sudo).
  \item Fenetre de confirmation de code : un autre agent a repris la place d'agent par defaut
    (par exemple \texttt{bluetoothctl default-agent}) ; le dashboard la reprend en 15~s maximum.
\end{itemize}

\subsection{Le dashboard ne se ferme pas}

\begin{itemize}
  \item Utiliser Échap, Ctrl+Q, Ctrl+C ou \texttt{systemctl -{}-user stop dashboard}.
  \item Un message \texttt{Thread ... did not stop in time} indique un thread bloque ;
    le processus est de toute facon termine apres 6~s (\texttt{alarm}).
\end{itemize}

\section{Limitations connues}
%% ===========================================================================

\begin{description}
  \item[Nom de l'appelant (HFP)]
    La propriete \texttt{Name} de \texttt{org.ofono.VoiceCall} est generalement vide
    avec les telephones Android modernes. Seul le numero (\texttt{LineIdentification})
    est affiche de maniere fiable.
  \item[Jaquette Bluetooth (AVRCP Cover Art)]
    BlueZ ne supporte pas AVRCP~1.6 de maniere stable. La jaquette est recuperee via
    l'API iTunes Search, ce qui necessite une connexion Internet et introduit un
    delai au changement de piste.
  \item[Format des notifications Google Maps]
    NavRelay depend de la disposition des notifications de Maps, qui n'est pas documentee
    et peut changer. Le classement par contenu (ETA / distance / action) et le filet de
    securite limitent l'impact ; \texttt{adb logcat -s NavRelay} permet de diagnostiquer.
  \item[Accents]
    Les polices LVGL integrees etant ASCII, les accents sont remplaces par la lettre simple.
  \item[Canal RFCOMM variable]
    Le canal assigne à \texttt{NavJsonService} par Android peut changer à chaque
    redemarrage. Ce cas est gere automatiquement par \texttt{nav-bind-daemon.sh}
    via le registre SDP.
  \item[Widget Bluetooth du bureau]
    Il est retire de la barre des taches pour eviter ses fenetres ; l'appairage se fait
    uniquement par le bouton Pair (ou \texttt{bluetoothctl}).
  \item[\texttt{sdptool}]
    \texttt{nav-bind-daemon.sh} utilise \texttt{sdptool}, deprecie dans BlueZ~5 ; il necessite
    que \texttt{bluetoothd} tourne en mode compatibilite sur certaines installations.
\end{description}
